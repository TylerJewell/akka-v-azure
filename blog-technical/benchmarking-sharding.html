Benchmark · Database sharding

Benchmarking database sharding in Akka.

Akka 24.05 shards event storage across ordinary PostgreSQL instances. One database handles 27k writes per second. Eight of them, in parallel, cross a million. The cost per IOPS stays flat.

Andrzej Ludwikowski · Principal Engineer
Jun 4, 2024 · 6 min read

Akka 24.05 introduced a significant feature: database sharding for event storage. This innovation allows developers to achieve unprecedented throughput with ordinary relational databases like PostgreSQL — throughput that normally requires high-priced databases. In this post we walk through a benchmark that scales from one Postgres instance up to eight, watch the throughput climb, and confirm that the cost per IOPS holds nearly flat.

Section I · Benchmark setup

An IoT digital twin under load.

To evaluate the new database sharding feature, we built a small Akka application that emulates a digital-twin solution for IoT devices. Each device keeps track of the last ten updates, simulating some complex failure-detection logic when processing a new update and putting real pressure on the persistence layer.

The load generator was Gatling. Each scenario tested a mixed load — 75% reads, 25% updates. Throughput was raised gradually until we hit the ceiling for a given setup, then held for 20 minutes.

Section II · Results across shard counts

One database. Two. Four. Eight.

At one database, the cluster reached 27k writes per second — impressive for a single Postgres instance. Doubling to two databases pushed throughput further, at the cost of some latency. Four databases produced a nearly linear climb. Eight databases crossed a million requests per second in Grafana — a satisfying number to watch tick over.

Section III · The scaling shape

Close to linear across four doublings.

The benchmark results reveal a compelling story of scalability. As we increase the number of database instances from one to eight, we observe near-linear throughput growth. The ability to distribute write operations across multiple databases while maintaining data consistency is the key factor in this performance boost. By alleviating pressure on any single database, Akka lets each instance operate more efficiently.

Perfect linear scaling is rare in real-world scenarios — network latency, coordination overhead, and hotspots in data distribution introduce some deviation. But the shape holds.

Section IV · Cost per IOPS

The economic outcome is a flat line.

Throughput scales; cost does not scale up. Cost per 1000 IOPS per month varies from $24.32 to $28.78 across all four configurations — essentially flat. All calculations use one-year reserved instance pricing.

Ordinary PostgreSQL instances now reach throughput levels that previously required specialized database systems. Organizations use their existing PostgreSQL expertise and infrastructure without paying for the higher licensing and operational overhead of a specialized store.

Section V · The takeaway

Moderate hardware today keeps both scaling axes open.

For an architect, the specific throughput figures matter less than the property they demonstrate. A moderate Postgres instance today keeps the horizontal scaling option open for tomorrow. Both scaling axes are available, and the cost per unit of throughput stays constant across configurations.

"Database sharding for event storage" delivers a growth curve that keeps its slope through every doubling — the shape a production planner actually needs.
