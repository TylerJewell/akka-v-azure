Distributed systems · Replicated event sourcing

Active-active without a distributed database.

Two customers book the same seat, in two regions, at the same instant. Database last-writer-wins drops one reservation without a rebook. Replicated Event Sourcing pushes the decision into the entity, where the domain knows the answer.

Johan Andrén · Akka Persistence team
May 24, 2023 · 9 min read

For many types of services it is important to provide low latency and high availability for business-domain entities. Achieving both requires being able to read and update state for the same entity in multiple physical locations — data centers or cloud regions. Traffic for a user can then be directed to the closest region for low latency, and fail over to another region if an outage takes the primary offline. Active-active also distributes load across regions rather than concentrating everything on one.

Terms A replica is a full copy of the entity in a specific region. Every replica accepts writes locally. Events are replicated between replicas, not directly between databases.

A complex aspect of active-active is conflict resolution, especially at the business level, when two conflicting updates happen in two different locations, or when a change happens just before an outage and does not replicate before the failure. Database replication tools usually resolve conflicts by time and let the last writer win. That is not always a satisfactory answer.

Two flight customers book the same seat on the same flight. Let the timing of a database write decide which passenger keeps the seat, and drop the other reservation on the floor — no rebook, no notification. The tool defaults to that behaviour when no one supplies business logic.

Section I · The shape of the problem

Reads and writes in every region, without a shared database.

Section II · The mechanism

Replicated Event Sourcing = event sourcing + CRDTs.

Replicated Event Sourcing in Akka combines Event Sourcing with Conflict-Free Replicated Data Types. Each replica persists events to its own local database instance. The database has no replication responsibility. Events cross regions over an efficient gRPC channel. The APIs are the same as for Akka Event Sourced Behaviors, with small additions for the replica identity.

Every ordering of events over a given item lands on the same quantity. That is the CRDT property, expressed at the domain layer rather than the storage layer. Why the signed-quantity trick works

The core requirement dictates every downstream choice: applying all events, in any order, must arrive at the same state. That is what makes conflicts resolve without a coordinator. It is also what dictates the shape of the events an author is allowed to write.

The shopping-cart example.

The cart accepts four commands — AddItem, RemoveItem, Checkout, Get. It stores two events during normal life, ItemUpdated and Closed, and a third, CheckedOut, on final settlement. The state is a map from item id to quantity, plus a set of replica ids that have observed the close.

// A single event type covers both add and remove, distinguished by sign.
public static final class ItemUpdated implements Event {
  final String itemId;
  final int quantity;   // positive = add, negative = remove
}

// The command handler for the OPEN state — cart is still accepting changes.
private ReplyEffect<Event, State> openOnAddItem(State state, AddItem cmd) {
  return Effect()
    .persist(new ItemUpdated(cmd.itemId, cmd.quantity))
    .thenReply(cmd.replyTo, updated -> StatusReply.success(updated.toSummary()));
}
private ReplyEffect<Event, State> openOnRemoveItem(State state, RemoveItem cmd) {
  return Effect()
    .persist(new ItemUpdated(cmd.itemId, -cmd.quantity))
    .thenReply(cmd.replyTo, updated -> StatusReply.success(updated.toSummary()));
}

Turning both commands into one signed-quantity event is what makes the state eventually consistent. Every ordering of events over a given item lands on the same quantity. That is the CRDT property, expressed at the domain layer rather than the storage layer.

The dividend No global coordinator. No last-writer-wins. No seat dropped on the floor. Every replica converges on the same state as long as every event eventually arrives. Latency stays local; conflict resolution stays in the domain.

Section III · The global sync point

Checkout requires every replica to agree.

Some transitions cannot be eventually consistent. Once a cart checks out we want to hand it to an order service, take payment, and ship. If we saw a local Closed event we cannot yet assume other replicas did not accept an ItemUpdated a moment earlier — we have not seen those events yet. So the entity needs a global synchronization point.

The trick is to model it in the event stream. The state carries a set of replica ids that have observed the close. When the local replica sees a Closed from any other replica, it triggers a CloseForCheckout command against itself, which persists a Closed event stamped with its own replica id. Eventually every replica has emitted its own Closed event, and every replica has observed all of them.

One replica — deterministically elected — waits until the observed-closes set equals the full replica set, then persists the final CheckedOut event. That event carries a wall-clock timestamp and is the signal downstream services consume.

Leader derivation from the entity id.

The leader is derived — no election protocol, no ZooKeeper, no lease. Every replica computes the same function over the entity id: sort the replica ids, hash the entity id, index into the sorted list. Same input, same answer, every replica agrees without talking.

private static boolean isShoppingCartLeader(ReplicationContext ctx) {
  List<ReplicaId> ordered = ctx.getAllReplicas().stream()
      .sorted(Comparator.comparing(ReplicaId::id))
      .collect(Collectors.toList());
  int idx = Math.abs(ctx.entityId().hashCode() % ordered.size());
  return ordered.get(idx) == ctx.replicaId();
}
The trade Waiting for every replica to observe the close means every replica must be reachable before checkout can complete. The pattern fits a cart, where checkout is a rare, transactional event and the customer will accept a moment's wait for consistency. For a hot counter, use eventual convergence and skip the sync.

Section V · When to reach for it

Anything with a per-entity conflict story.

Replicated Event Sourcing fits when the domain has an opinion about how conflicts should resolve. Carts, reservations, wallets, inventory, matchmaking — anywhere a bare last-writer-wins would produce results the business would not accept. For write-once ledger data or append-only telemetry, plain event sourcing is enough. For read-heavy caches, a read-replica pattern is simpler.

The rule of thumb: if you have ever had to explain to a business owner why two updates arriving within a second produced the wrong outcome, this is the pattern that lets you write the right one in code.
