Adaptive stream parallelization for fun and throughput.

The mapAsync operator lets a stream do N things at once. When those things contend, cranking N up hurts more than it helps. A new operator, mapAsyncPartitioned, lets the stream reason about contention explicitly — and the benchmark says the effective ceiling rises by a factor of five.

Levi Ramsey · Akka Streams team
15 May 2023 · 6 min read

Akka Streams is one of the foundational components at the core of Akka, and the most notable new feature in Streams for the 23.05 release is the introduction of a new operator, mapAsyncPartitioned. This operator improves on the performance of the existing mapAsync operator in situations where mapAsync over-parallelizes: as a consequence, it is more able to squeeze out the maximum amount of parallelism. Systems built on it accomplish more overall while reducing resource requirements.

Akka users often use mapAsync in streams which need to interact with the world outside the stream — delivering events to actors for stateful processing, writing to an external system or database as part of CQRS. The value proposition is straightforward: keep the stream's steady rhythm, but let downstream side effects happen concurrently.

Recap mapAsync(N) keeps at most N futures in flight, then emits results in the same order they arrived. Great for concurrency without reordering. Bad when the N futures fight each other for the same resource.

One might write the following stream using Akka 2.6, to consume messages from Kafka and deliver them to actors distributed across a cluster using Akka Cluster Sharding:

RestartSource.onFailuresWithBackoff(restartSettings, () ->
  Consumer.committableSource(consumerSettings, subscription)
    .mapAsync(askParallelism, kafkaMessage -> {
      var entityId = kafkaMessage.record().key();
      var content  = kafkaMessage.record().value();
      var offset   = kafkaMessage.committableOffset();
      return sharding.entityRefFor(entityTypeKey, entityId)
        .ask(replyTo -> new MyActor.MessageFromKafka(content, replyTo),
             Duration.ofMillis(500))
        .thenApply(done -> offset);
    })
    .via(Committer.flow(committerSettings))
);

However, askParallelism has a peak. Past the peak, throughput falls. The benchmark shows a curve that peaks and then collapses:

The reason is that it is possible for stream elements A and B to contend with one another in their processing so that being in-flight at the same time delays each other's completion. In this benchmark, the major contention occurs because the messages in the respective asks are to the same sharded entity and queue up in the actor's mailbox. Similar dynamics appear when ACID transactions conflict and need to be retried under contention on a SQL database.

In any system where efficient resource usage is a priority, there is a hard maximum level of realizable parallelism. In practice, though, the throughput-maximizing level of parallelism depends on keeping contention within some window that varies across real-world streams over time. A constant value for parallelism in a mapAsync stage forces a compromise across every workload phase.

1The observation that changes the operator

Parallelism is per-partition.

The key insight behind mapAsyncPartitioned is that most contention is partitioned. Two calls to the same sharded actor contend. Two calls to different sharded actors do not. The right parallelism ceiling is two numbers: a global cap on in-flight work, and a smaller cap on in-flight work per partition.

Rewritten against Akka 2.8 (the 23.05 release):

Function<CommittableMessage<String, byte[]>, EntityRef> entityRefExtractor = kafkaMessage -> {
  var entityId = kafkaMessage.record().key();
  return sharding.entityRefFor(entityTypeKey, entityId);
};

RestartSource.onFailuresWithBackoff(restartSettings, () ->
  Consumer.committableSource(consumerSettings, subscription)
    .mapAsyncPartitioned(
      askParallelism,        // overall max in-flight across all entities
      2,                     // max in-flight per entity
      entityRefExtractor,    // assigns incoming element to a partition
      (entityRef, kafkaMessage) -> entityRef.ask(
        replyTo -> new MyActor.MessageFromKafka(
          kafkaMessage.record().value(), replyTo),
        Duration.ofMillis(500))
      .thenApply(done -> kafkaMessage.committableOffset())
    )
    .via(Committer.flow(committerSettings))
);

The 2 is the interesting number. It says: at most two asks may be in flight for any single entityRef. The entityRefExtractor assigns each stream element into a queue keyed by its target entity. Only two elements per queue advance at any moment. Once the queue drains, the next elements move up.

The overall stage still respects askParallelism. If askParallelism is 1000 but the next 1000 elements all target the same entity, the effective concurrency is 2 — the stream adapts.

The trade. You pay a small allocation cost per element (one queue slot). In exchange the stream reasons about contention explicitly and stops fighting itself when hot keys arrive. On workloads with any partition skew, the exchange is one-sided.

3When to reach for it

Anything with a shard-shaped downstream.

Any stream that fans out to sharded actors, per-key databases, per-tenant caches, or anywhere else where two operations against the same key contend is a candidate. If the downstream is fully independent — a stateless HTTP call to a horizontally-scaled service — plain mapAsync is enough. The rule of thumb: if you have ever tuned askParallelism down to protect a downstream, mapAsyncPartitioned is what you actually wanted.
